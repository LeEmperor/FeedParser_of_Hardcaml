# OCaml and Dune synthesis reporting

Adopt the `hardcaml_networking` reporting pattern: a Dune-built OCaml command
selects typed Hardcaml circuits, uses `hardcaml_xilinx_reports` to generate
projects, and validates and summarizes the resulting Vivado reports. The
package's exact name is `hardcaml_xilinx_reports`, with OCaml module
`Hardcaml_xilinx_reports`; there is no generic `hardcaml_reports` integration
being extracted here.

This integration is implemented in the current `cme/` checkout, whose Dune
package is `feed_parser_of_hardcaml`. `synthesis/xilinx_reports.ml` registers the
CME targets; `synthesis/report_support.ml` adapts networking's wrapper, with
failure-path inline tests in `report_support_tests.ml`.
Use [test_architecture.md](test_architecture.md) for functional verification and
the [parser plan](cme_mdp3_10g_parser_plan.md) for acceptance requirements.

## Two Dune entry points with different evidence

```text
dune runtest
  OCaml scenarios -> Step/Cyclesim -> typed observations -> assertions/goldens

dune exec synthesis/xilinx_reports.exe -- <target> <flags>
  typed Hardcaml create function + Scope/circuit database
    -> hardcaml_xilinx_reports
    -> generated Verilog + clock XDC + Tcl
    -> Vivado, only with -run
    -> checked report files + OCaml terminal summaries
```

The reporting chain remains authored and orchestrated in OCaml, with an
explicit Dune target. Vivado still performs FPGA synthesis and timing analysis;
the OCaml library does not replace the device tool. Generated Verilog and Tcl
are normal backend artifacts. The optional `@rtl-check` alias retains only Yosys hierarchy resolution and
Icarus Verilog elaboration; these checks provide no device timing/resource result.

Keep reporting separate from `lib/common/generate.exe`, as networking does.
The reports library generates RTL from the selected circuit itself. Keep
ordinary `dune runtest` independent of a Vivado installation or license;
invoke device reporting explicitly. Dune builds the OCaml executable, while
its CLI performs external report generation when requested.

## Implemented entry point

The executable's principal dependencies are shown below. The actual
[synthesis/dune](../synthesis/dune) also links `cme_report_support` for artifact
validation and `stream_test_support` for the transport-only fixture:

```lisp
(executable
 (name xilinx_reports)
 (libraries
  async
  core
  core_unix
  core_unix.command_unix
  hardcaml_xilinx_reports
  cme_of_hardcaml)
 (preprocess (pps ppx_jane)))
```

The packages `hardcaml_xilinx_reports`, `async`, and `core_unix` are declared in
`dune-project`; the opam file is regenerated by Dune. Use the
existing `./scripts/with-switch.sh` wrapper and a reports version compatible
with that switch's Hardcaml. Networking records its initial integration with
OCaml `5.2.0+ox`, Dune `3.22.2`, and Hardcaml/reports
`v0.18~preview.130.106+341`; that is provenance, not a newly verified installation
requirement for this checkout.

The `report_command` and artifact helpers are adapted from networking with
source provenance recorded in the file header. Preserve that attribution when
editing, following [project conventions](hardcaml_project_conventions.md).
Do not copy networking's lint stanza without introducing the corresponding
local lint setup.

The typed registration shape is:

```ocaml
open! Core
open! Async
open! Cme_of_hardcaml
module Reports = Hardcaml_xilinx_reports
module Parser_command =
  Reports.Command.With_interface (Cme_feed_parser.I) (Cme_feed_parser.O)

(* Inside Command.group, after adapting networking's report_command helper: *)
let parser_command =
  report_command ~name:"cme_feed_parser" (fun flags ->
    Parser_command.run
      ~primitive_groups:[]
      ~name:"cme_feed_parser"
      ~flags
      (fun scope inputs ->
        Cme_feed_parser.create ~config:Cme_config.default scope inputs))
;;
```

This is a registration sketch, not a standalone executable: `report_command`
must include the validation below and the command must be registered under a
CLI name such as `cme-feed-parser`. The empty primitive list follows networking's
Artix-7 workaround; reconsider it for other devices after validating counts.

Current CLI targets are `ingress-fifo` (depth 64), `event-fifo` (depth 16),
`byte-aligner`, `stream-foundation` (ingress depth 64 plus aligner), and
`cme-feed-parser` (inactive skeleton). Parameters are fixed in the adapters and
printed with each invocation. Add architectural parser paths and the complete
parser as they become available.
Fix optional parameters such as FIFO depth in explicit adapters matching the
typed interface. Record those parameters with the result. Reporting the
inactive Phase 0 top is only a generator smoke test, not useful parser area or
throughput evidence. Select hardware primitive implementations for synthesis
if any future DUT offers separate simulation models.

## Preserve hierarchy through circuit construction

Reporting discovers circuits in `Scope.circuit_database`; OCaml module names
and nested source files alone do not create synthesis hierarchy. Use the
Hardcaml `create`/`hierarchical` pattern for intended child boundaries, passing
the provided scope through construction. Keep a flattened scope for Cyclesim
fixtures and retain hierarchy for report elaboration.

The Phase 0 structural suite checks the parser wrapper and the transport
fixture's registered children and full RTL definitions. The optional Yosys
hierarchy check verifies their resolution in emitted Verilog.
An intentional vendor primitive needs its supported external implementation;
do not confuse it with a missing portable child implementation.

| Flag | Meaning in the inspected reports library |
| --- | --- |
| `-hierarchy` | Generate projects for the top and each circuit in its database. |
| `-full-design-hierarchy true` | Include child implementations within each generated project; use for path/top timing and inclusive area. |
| `-full-design-hierarchy false` | Emit children as black boxes, useful for local resource attribution. This is the upstream default; specify it explicitly. |
| `-flatten` | Flatten during Hardcaml elaboration, removing boundaries before project enumeration. |
| `-dont-flatten-hierarchy` | Ask Vivado to preserve synthesis hierarchy; an attribution/debug profile, not networking's normal timing profile. |
| `-place`, `-route` | Extend synthesis to placement, then routing; `-route` alone is ignored. |

Do not sum inclusive parent and child resource reports: that double-counts
children. Do not claim end-to-end timing from a project whose children are
black boxes. When enumerating hierarchy, check that each project's XDC has
the expected clock: the inspected library filters clocks by circuit input name.

## Commands

All commands below run from this checkout's root. Target `cme-feed-parser`
and report name `cme_feed_parser` are implemented registrations; use an
implemented Phase 1 target for meaningful hardware smoke evidence.

```sh
./scripts/with-switch.sh dune build synthesis/xilinx_reports.exe
./scripts/with-switch.sh dune exec synthesis/xilinx_reports.exe -- -help
./scripts/with-switch.sh dune exec synthesis/xilinx_reports.exe -- cme-feed-parser -help
```

Example project generation with no Vivado invocation, using networking's
Artix-7 part only as a functional-platform example:

```sh
./scripts/with-switch.sh dune exec synthesis/xilinx_reports.exe -- cme-feed-parser \
  -dir _build/xilinx-reports/dry-run \
  -part xc7a100tcsg324-1 \
  -clock clock_i:25 \
  -full-design-hierarchy true
```

For a timing-oriented run against a deliberately selected part, set
`REPORT_PART` to its full device identifier, then run:

```sh
./scripts/with-switch.sh dune exec synthesis/xilinx_reports.exe -- cme-feed-parser \
  -dir _build/xilinx-reports/timing \
  -part "${REPORT_PART:?Set REPORT_PART to the chosen FPGA part}" \
  -clock clock_i:156.25 \
  -hierarchy \
  -full-design-hierarchy true \
  -jobs 1 \
  -run
```

`-clock` takes `port_name:frequency_in_MHz`; use the actual `clock_i` port,
not networking's leaf `clock` name. A 156.25 MHz constraint tests the intended
application frequency; it does not establish that the chosen device meets it.
For local resource attribution, change the output directory to
`_build/xilinx-reports/resources` and use `-full-design-hierarchy false`.

Add `-full-report` to print full standard reports. Add `-path-to-vivado /path/to/Vivado/bin/vivado` if needed. Start
with explicit `-jobs 1`: despite help text mentioning one, the inspected
hierarchical runner uses eight concurrent jobs when the option is absent.
For future multi-clock targets, repeat `-clock` for each real clock port and
retain the limitations below.

## Report validation is part of the command

Preserve these behaviors from networking's wrapper:

1. Force `flags.reports = true`. Always request standard Vivado utilization
   and timing reports, even without the upstream `-reports` option.
2. Determine the final stage from the flags: `post_synth`, `post_place`, or
   `post_route` (routing requires placement).
3. Before execution, record existing artifact modification times. After
   execution, require the selected target's three files to exist, be nonempty,
   and have newer modification times if they existed before the run:
   `<dir>/<name>/<stage>_report.txt`,
   `<dir>/<name>/<stage>_<name>.utilization`, and
   `<dir>/<name>/<stage>_<name>.timing`.
4. Print curated resource rows, setup/hold/pulse-width summary lines, and
   artifact paths. Print complete standard reports with `-full-report`.
5. Without `-run`, report project generation only; no timing/resource success
   may be inferred from files left by an earlier execution.

This protects against the inspected upstream runner returning missing reports
after a failed Vivado subprocess without necessarily failing the command.
Networking validates the selected target's artifacts. For a future financial
command claiming success for *all* `-hierarchy` projects, extend validation to
every generated project; its current top-only wrapper does not prove that.
Fresh per-run output directories also avoid stale-report ambiguity.

Networking disables compact primitive-group queries because their
UltraScale-oriented properties give misleading zero counts for its Artix-7
`xc7a100t`. It uses the standard utilization report as authoritative. Treat
empty/missing results as failed evidence, and validate device-specific labels
before reusing its resource-row parser on another FPGA family. A completed
report run with negative slack is still a timing failure; artifact freshness
does not check timing acceptance.

## Acceptance and limits

Keep generated projects, reports, and logs under `_build/xilinx-reports/`.
Record the source revision, circuit and parameters, package/tool versions,
device part, clock constraints, exact command, hierarchy profile, stage,
resource counts, slack, and report paths for any claimed result. Dry generation
checks project emission; a successful Vivado run checks backend execution;
meeting an explicit timing budget is a separate conclusion.

These are out-of-context estimates. The generated constraints principally
declare clocks (and an optional clock-source location); they do not provide
board pin assignments, I/O delays, asynchronous clock groups, or a complete
CDC/signoff constraint set. Even placed/routed out-of-context reports do not
replace integrated board timing closure, CDC analysis, DRC, or bitstream checks.

The parser plan's Phase 6 still needs independent evidence for functional
conformance, one accepted 64-bit beat per cycle under the stated conditions,
the eight-cycle event latency bound, complete RTL hierarchy, combinational
loop checks, and review for unintended wide muxes. OCaml circuit inspection
and Dune tests can own structural checks; synthesis results complement them.
A utilization/slack summary alone does not discharge every structural check.
The Arty 25 MHz functional path cannot establish 10G timing or throughput.

The [Phase 0–1 verification record](phase01_verification.md) records the build,
generation, backend smoke, failure handling, and independent functional test
evidence for this implementation. If device tools
or the final 10GbE target are unavailable, record that missing evidence without
substituting a different toolchain or presenting a smoke run as signoff.
